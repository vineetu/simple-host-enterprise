Enterprise

A place for internal AI-built pages that would actually pass review

Employees build web pages with AI coding agents faster than any pipeline can review them. Simple Host for enterprises is the smallest thing that lets that happen safely: one binary, your own identity provider, and an origin boundary between every employee's work.

01 — The problem

An agent can build a page in minutes. Getting it hosted safely takes weeks.

A coding agent can turn an idea into a working internal tool — a dashboard, a tracker, a small app with its own data — in one sitting. What it can't do is get that page a URL without either a manual deploy request or a shortcut nobody signed off on. Every shortcut we found in the instance this package replaces looked the same: a plaintext key standing in for identity, a state endpoint nobody authenticated, sites sharing an origin they shouldn't have.

None of that is a flaw in any one line of code. It's what happens when a tool built for a hackathon quietly becomes the thing people actually rely on.

02 — What it is

Static hosting plus a database, and nothing else

A site on Simple Host is three things: static files, a per-site JSON state document the page's own JavaScript reads and writes, and assets — files a page stores at runtime and serves back, like an upload or a generated image. That's the whole product surface. There's no server-side code to run, no function runtime to secure, no build pipeline to own.

Every employee gets a namespace at their own hostname the moment they sign in. Publishing is an API call, and an agent can make it directly — through the REST API, through MCP, or through a packaged skill. The browser dashboard is a convenience for a person, not the only way in.

03 — Identity via what you already have

Sign in with your company's SSO. There is no other way in.

Okta, Google, Azure AD — any OpenID Connect provider your company already runs. An account is created by signing in, not by a registration form, and there's no key that stands in for a person: an API key is something a signed-in person mints for their own agent, never the identity itself. Admin status follows a claim or an email list your platform team controls, refreshed on every sign-in — never a value baked into the binary.

Offboarding is one action: disable the person, and every session and key they hold stops working immediately, everywhere, without touching the sites they built.

04 — Every site on its own address

Origin isolation is the architecture, not a migration target

Every site serves at its owner's own subdomain, from day one — no shared control-plane origin, no legacy path, no flag to flip later. That single decision is what makes the rest of the security story simple to state:

  • A page's script can only read and write its own owner's state and assets — never a colleague's.
  • A site can be restricted to a named list of viewers, served on its own hostname, refusing everyone else as if it didn't exist.
  • Nothing about viewing or calling a site's API depends on a header a terminal can forge. The identity comes from a real, revocable session tied to that host.
05 — Teams, with one role

Anyone on the team can do anything the team can do

A team is a namespace, the same as a person's. Deliberately, there's no permission matrix inside it — every member can publish, roll back, or manage the team's sites. The control that matters is knowing who did what, not gating who's allowed to try, which is why the audit trail below is a requirement and not an add-on.

06 — Everything is logged, and you can see it

An action audit and a visitor log, both queryable and exportable

Every mutation — a publish, a rollback, a visibility change, a membership change, every admin action — writes an audit row inside the same transaction that makes the change, so there is no path to a change with no record. Separately, every visit to a site is logged with the visitor's real identity from your SSO provider, including the owner's own visits, which is what turns "who looked at this" from a guess into an answer.

Owners see the activity and visitors for their own sites in the dashboard; admins see everything and can export both as CSV or JSONL for the systems that already collect your logs. Retention is a monthly job under the database's own owning credential, never the application's own connection.

07 — What runs where

One binary, Postgres, a volume, a bucket — on any Kubernetes

The whole application is a single Go binary. It needs a Postgres database, a persistent volume for site files, and an S3-compatible bucket for backups — nothing AWS-specific, nothing that only works on one cloud. Deploys are image-based Kubernetes rollouts with a migration step that runs first and blocks the rollout until the schema is current, never a binary copied into a running pod by hand.

Encryption at rest is a requirement your platform meets with your own cluster and cloud: an encrypting storage class, a managed database with point-in-time recovery, a bucket with default encryption. What the application itself adds on top is a server-side-encryption header on every backup object, and an optional client-side envelope so a compromised bucket alone still isn't enough.

08 — Installing it

From an empty cluster to a signed-in dashboard, in order

The install guide takes a platform team from nothing to a working instance: first on a local cluster with no cloud account at all, so the whole shape is provable before anything touches production; then on a real cluster with your own managed Postgres and bucket; then your OIDC provider's setup checklist; then backup, restore, and upgrade. Every command in it is one that exists in the repository today — nothing hypothetical, nothing to reverse-engineer from a Kubernetes manifest.

See the checklist, a copy-paste agent prompt, and the by-hand commands.

A security review pack ships in the same repository: a threat model, a control mapped to every finding from the audit that produced this package, a pen-test checklist, and the limitations the software accepts rather than hides.

09 — Extension points

Documented seams, not a plugin system

A company whose pages need to call an internal model has one documented seam to add a forwarder: a handler on the site's own host that receives the authenticated session, applies the site's write rule, and meters usage per person and per site — the same shape the package's own removed AI-gateway proxy used, kept as the reference. Identity-provider quirks that a configuration value can't express get a small claim-mapping function per provider. The storage layer sits behind one interface if a future release ever needs something other than a mounted volume.

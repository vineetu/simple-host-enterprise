Install

Bring up Simple Host on a cluster you already have

Three ways to read this page: check what you need, paste one prompt into a coding agent and let it drive the checkout for you, or run the commands yourself. All three follow the same path documented in docs/install.md in the package repository.

1 — What you need

A short checklist a platform team prepares first

  • A Kubernetes cluster and a kubectl context that reaches it. Docker Desktop or minikube for a first look; anything real for production.
  • A Postgres you can reach.Or: no Postgres yet — the package ships an in-cluster overlay (deploy/components/postgres-incluster) for a first look.
  • An S3-compatible bucket.Or: no bucket yet — the package ships an in-cluster MinIO overlay (deploy/components/minio) for a first look.
  • A wildcard DNS name for the base host, and a way to issue its certificate. A real domain plus a cert-manager DNS-01 ClusterIssuer for production; for a first look, a public wildcard name that already resolves to loopback (nip.io or sslip.io) plus mkcert needs nothing from DNS at all.
  • An OIDC client from your identity provider — Google, Okta, Entra ID, or any other OpenID Connect provider your company already runs — with its issuer URL, client ID, and client secret, and the ability to register a redirect URI shaped https://<base-host>/auth/callback.

Nothing else. No cloud account is required to try the package end to end; sections 2 and 3 below cover both a first look and a real install.

You are installing Simple Host for enterprises from this checkout of the
repository. Do not skip reading the docs, and do not invent a file, a
Makefile target, or a default value that isn't already in this tree.

1. Read docs/install.md in full before touching anything.

2. Ask me for exactly these values, and nothing else, before making any
   change:
   a. Which kubectl context should you use, and does
      `kubectl --context <that context> cluster-info` succeed?
   b. Do I have a Postgres you can reach, or should you deploy the
      in-cluster overlay (deploy/components/postgres-incluster)?
   c. Do I have an S3-compatible bucket you can reach, or should you
      deploy the in-cluster MinIO overlay (deploy/components/minio)?
   d. What wildcard hostname should the base host use, and how will its
      certificate be issued: mkcert against a local nip.io/sslip.io
      hostname, or a named cert-manager ClusterIssuer for a real domain?
   e. My OIDC provider's issuer URL, client ID, and client secret, and
      whether I have already registered the redirect URI
      https://<base-host>/auth/callback with it.

3. If I said "no" to (b) and (c) and gave a nip.io/sslip.io hostname in
   (d), follow docs/install.md sections 2-4 (the local-cluster path):
   run `make local-tools`, then `make local` (add
   CLUSTER_CONTEXT=minikube and tell me to run `minikube tunnel` if I'm
   on minikube) — these are the exact Makefile targets in this
   repository; do not substitute your own kubectl/kustomize sequence
   where a target already exists.

4. Otherwise, follow docs/install.md section 5 (the real-cluster path):
   - Copy deploy/overlays/byo/config.env.example to config.env and
     deploy/overlays/byo/secrets.env.example to secrets.env; fill in only
     the values I gave you in step 2, plus anything docs/configuration.md
     marks required — never invent a value I didn't give you.
   - Place my database's CA bundle at deploy/overlays/byo/db-ca.crt.
   - Edit deploy/overlays/byo/ingress-patch.yaml with my real hostnames
     and ClusterIssuer name.
   - Edit deploy/overlays/byo/kustomization.yaml's images: digest to the
     image reference I give you; ask me for it rather than guessing a tag
     if I haven't built one. Use `make build` and/or `make image` only if
     I ask you to build it yourself.
   - Apply with `kustomize build deploy/overlays/byo | kubectl apply -f -`,
     then `kubectl -n simple-host rollout status deploy/simple-host`.

5. Either way, verify readiness through the ingress, not by
   port-forwarding around it:
   `curl https://<base-host>/readyz`
   (add `--cacert "$(mkcert -CAROOT)/rootCA.pem"` only on the local
   mkcert path) and confirm it returns {"status":"ok"}.

6. Verify a first sign-in: open https://<base-host>/auth/login
   yourself, or walk me through opening it, and confirm the dashboard
   loads with a key-minting form.

7. Report back: the dashboard URL, which path you took, and anything
   from docs/install.md's troubleshooting section you actually hit along
   the way.

8. Restricted sites, the site-facing state/asset API, and the audit/
   access-log trail are all built — docs/install.md sections 6, 7, and 8
   have real steps if I ask you to verify any of them, including reading
   GET /api/audit and GET /api/access back and, if I'm an admin, trying
   the CSV/JSONL export at GET /api/admin/export.

The agent should stop and ask if any answer in step 2 is missing — it should never guess a hostname, a provider, or a database.

3 — Install by hand

The same path, as commands, on one screen

The quickest way to see the whole thing working, no cloud account needed:

# 1. Check tools and cluster reachability
make local-tools

# 2. Bring up ingress-nginx, cert-manager, Postgres, MinIO, Dex, and the app
make local
# minikube instead of Docker Desktop: make local CLUSTER_CONTEXT=minikube
# (run `minikube tunnel` in another terminal first)

# 3. Confirm it's ready
curl --cacert "$(mkcert -CAROOT)/rootCA.pem" \
  https://simple-host.127-0-0-1.nip.io/readyz

# 4. Sign in — open in a browser
https://simple-host.127-0-0-1.nip.io/auth/login
# admin@example.com / adminpass, or person@example.com / personpass

# 5. Run the end-to-end check
make smoke

# 6. Tear it down when you're done — data is disposable
make local-down

For a real cluster with your own Postgres, bucket, and domain, the same six steps become section 5 of docs/install.md — the file the agent prompt above reads for you.
